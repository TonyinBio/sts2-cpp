# Domain docs

This repo uses a single-context layout:

- GLOSSARY.md at the repository root
- docs/adr/ for architecture decisions

Read `docs/specs/README.md` to find detailed contracts, design proposals, audit evidence
and implementation status. Preserve their different evidence levels: a design target
or requirement does not establish implemented or reference-verified behavior.

Before exploring code, read the glossary and ADRs relevant to the work.
If they do not exist, proceed silently. The domain-modeling skill
creates them when terminology or decisions are resolved.

Use glossary terms consistently in issues, proposals, hypotheses,
and test names. Note meaningful terminology gaps for domain-modeling.

Explicitly surface any proposal that contradicts an existing ADR,
identifying the ADR and explaining why it should be reconsidered.
